# Архитектура 0.3.0

## Единственный production-проект

`Tolmach.csproj` включает `src/**/*.cs`; `build/RuntimeReferences.props`
задаёт ссылки из выбранного профиля. Тестовый проект ссылается на production DLL,
а не компилирует подмножество исходников. NUnit управляет discovery, assertions,
setup/teardown; VSTest пишет TRX. Build.ps1 запускает стандартную сборку/тесты,
передаёт проверенные файлы Thunderstore CLI и проверяет готовый пакет. Устанавливает
пакет менеджер модов (Gale, r2modman); собственного установщика нет.

## Данные и привязки

CatalogLoader использует Newtonsoft.Json, проверяет структуру данных и сопоставляет
GUID, точное имя сборки и `pluginVersion`. Версия пакета хранится отдельно. Нулевые
отсутствующие компоненты версии нормализуются, ненулевой revision не игнорируется.
Неуспешная повторная привязка очищает старую сборку, таблицу и разрешения.

Каталоги называются `tolmach-<id>.json`, и плагин читает только такие файлы.
Типы плагина вне namespace обозначаются в `namespaces` отметкой `<global>`: пустая строка
списка отвергается загрузчиком. Один ключ или одна сырая строка во всех каталогах переводится
одинаково: плагин пропускает ключ с разным английским или русским, а валидатор отклоняет такие
каталоги заранее.
LocalizationManager, встроенный во многие моды, считает своим переводом любой файл
`<имя плагина>.*` в папке BepInEx и падает на имени вроде `SleepSkip.json`.

У самой игры нет записи BepInEx. Модуль игры (субтитры) привязан к зарезервированному
GUID `valheim`: сборка `assembly_valheim`, объявляющая тип `Version`, и его
`CurrentVersion`. Такой модуль содержит только словарь, поэтому namespaces ему не нужны;
модулю с IL-адаптерами они по-прежнему обязательны.

`Plugin.cs` владеет жизненным циклом Harmony-патчей/подписок. По умолчанию IL-адаптеры
работают только на версиях из снимка. Неизвестная версия оставляет нативные ключи,
но не автоматически допускает неизвестный IL. `AllowOtherVersions` — явное исключение.

## Кто выполняет стандартные операции

Harmony владеет перечислением загружаемых типов, поиском полей/свойств по иерархии,
чтением инструкций, переносом IL labels и установкой detours. `RuntimeAccess` оставляет
только точность идентификации типа, выбор receiver при чтении и ключ диагностики
метода. Собственного декодера, обхода BaseType и навигационного Reflect.Path нет.

Jötunn владеет таблицами собственных scopes; адаптер вызывает публичные GetTranslations
и AddTranslation. В версии 2.30.2 язык передаётся `in string`; рефлексия учитывает String&.
Единственный доступ к внутреннему реестру нужен, чтобы получить scope **другого** мода:
публичный GetLocalization не является универсальным чужим lookup. Map не читается.

Встроенные LocalizeKey-менеджеры получают перевод через их Russian API. Если setter
отсутствует, прямой записи во внутренний словарь больше нет: выдаётся предупреждение,
сохраняется только доступный глобальный путь. Ключ регистрируется в fill-only защите
до вызова setter: он сразу пишет через AddWord, и чужой русский перевод этого ключа
в игровой таблице остаётся. Отдельные английские Localization не считаются
переключением языка всего интерфейса.

Глобальные игровые слова читаются через Translate и добавляются через AddWord. Наш код
решает только fill-only политику: отсутствующий/английский текст дополняется, имеющийся
чужой русский не заменяется нашим. Это правило действует и при возврате собственного
русского через Jötunn/native регистрацию. m_translations не записывается напрямую.

Заполняется только основной экземпляр Localization (`m_instance`). Моды создают и
отдельные экземпляры (SkillManager держит английский для имён разделов конфига);
конструктор игры временно загружает в каждый язык игрока, и русский, записанный туда,
попал бы в английские lookups. Язык основного экземпляра берётся из его
`GetSelectedLanguage` (PlatformPrefs игры, включая ключ Steam Deck), PlayerPrefs —
только запасной путь. Пока основной экземпляр строится, `m_instance` ещё пуст; язык,
выбранный в конструкторе (первый запуск по локали системы), и первое заполнение
применяются при ближайшем Refresh: Start плагина, меню, событие локализации Jötunn.

Для полной строки в игре есть отдельный cache. Узкий адаптер вызывает его штатный
EvictAll после регистрации/изменений. Публичного метода сброса в предоставленных
свидетельствах не установлено, поэтому доступ к m_cache пока остаётся. Этот частный
член и получение чужого scope — явно описанные ограничения интеграции, не скрытый
второй менеджер словарей.

## Что остаётся предметным кодом

TextEngine содержит точные таблицы, шаблоны на стандартном Regex с тайм-аутом и явно
типизированные параметры: непрозрачное значение, название поля, вложенное сообщение,
стандартная подпись карты и слово из именованного словаря (`term:<словарь>`): составное
название переводится, только если в словаре есть все его части, иначе остаётся
оригиналом целиком. Произвольная рекурсивная замена имён/ID не выполняется.
Кэш ограничен 1024 изменёнными результатами; неизвестные строки не сохраняются.

DisplayPatches выбирает только известные выводящие методы/поля в разрешённых namespace
загруженного мода. Словарные модули без UI-данных не сканируются. Literal-only модуль
не получает общий перехват всех UI-вызовов. Литеральные адаптеры охватывают и
конструкторы экземпляров: в них компилируются значения полей компонентов по умолчанию. В IL остаётся узкая логика сохранения
аргументов и перевода выбранных параметров — CodeMatcher сам не определяет их смысл.
На boundary/prefix местах нет небезопасного fallback; пропуск отражается в отчёте.
Правило литерала называет метод по имени, а у перегрузок имя общее, поэтому транспайлер
ставится только на тело, в исходном IL которого есть значение правила. Значение, которого нет
ни в одной перегрузке, отмечается при установке тоже по исходному IL.

AddPin и DiscoverLocation не считаются UI-приёмниками. PersistentUi меняет подпись
виджета, не PinData.m_name. Чужой перевод виджета сохраняется. Личное имя, буквально
совпавшее со стандартным, может отображаться переведённым; настройка отключения
доступна в Display.TranslateStandardMapLabels. Горячая смена настроек не поддерживается.

RawDisplay переводит сырые строки: текст, который мод хранит в объекте (названия и
описания предметов и эффектов, записи Compendium, составные имена существ и чертежей) и
который игра передаёт в `Localization.Localize` без ключа. Префикс `Localize` заменяет
такую строку до разрешения `$`-токенов, поэтому «$enemy_greydwarf Guardian» становится
«$enemy_greydwarf-страж», и игра сама подставляет «Грейдворф» и кэширует результат.
Сверяются вся строка, затем каждая строка текста между тегами разметки; поиск по
словарю — O(1), перед таблицами стоит общий кэш на 4096 строк (попадания и промахи).
Работает только для основного экземпляра `Localization` при русском языке и только для
модулей точной версии; хранимые поля объектов, рецепты и сохранения не меняются.
Прежние записи `prefabs` (два топора WackysDatabase, эффект MWL) идут тем же путём. ExtraHooks дополняет словари при
инициализации меню и переводит точное уведомление OreMines в `Chat.OnNewChatMessage`:
через этот метод принятое сообщение попадает и в журнал чата (`Terminal.AddString`), и
в надпись над игроком. Сами строки журнала чата объявлены в `Terminal` и в целевых
модах несут вывод консольных команд, поэтому общим приёмником они не считаются.

CllcAdapter обслуживает Creature Level and Loot Control. Мод не пользуется локализацией игры:
в своём Awake он один раз читает собственную YAML-таблицу `LocalizationWrapper` — роды существ,
шаблон таблички на каждый род, формы слов по родам, сообщения, значения перечислений, тексты
настроек. Tolmach грузится после него (мягкая зависимость). При русском языке адаптер кладёт в
приватное статическое поле `instance` таблицу из раздела `cllc`; если там уже русская таблица,
только дописывает отсутствующие записи. Роды, шаблоны и формы слов берутся одним блоком, чтобы
не смешать коды родов двух таблиц; плейсхолдеры каждой записи сверяются с английской таблицей
самого мода, а синтаксис шаблонов загрузчик проверяет по правилам мода. Всё остальное мод читает
из текущей таблицы при показе, поэтому патч Harmony не нужен, а отложенные патчи StartupAccelerator
на адаптер не влияют. Тексты окна настроек, которые мод записал в `ConfigurationManagerAttributes`
при привязке, пересчитываются его же функциями (`getSettingGroupTranslation`,
`getSettingTranslation`, `getTranslation`); имена секций и ключей `.cfg` не меняются.

Если тип, сигнатура или тело метода мода ссылаются на отсутствующую необязательную
зависимость, рефлексия бросает исключение. DisplayPatches и поиск LocalizeKey
пропускают только этот тип или метод с предупреждением в отчёте; остальные адаптеры
модуля и итоговые проверки ожидаемых адаптеров выполняются.

Метод с фильтром исключений (`catch … when`) или блоком `fault` не патчится. HarmonyX 2.9
не размечает обработчик фильтра и завершает обработчик `fault` (итераторы с `try/finally`)
командой `leave` вместо `endfinally`: патч не компилируется или даёт недопустимый IL даже без
изменений. Обычно ошибку
ловит обработка вокруг `Harmony.Patch`, но StartupAccelerator откладывает патчи до конца
загрузки плагинов, и тогда сбой останавливает игру. По той же причине о литерале, оставшемся
в теле метода незаменённым, сообщает сам транспайлер, когда план уже известен, а не код сразу
после `Patch`.

## Что не доказано чтением архитектуры

Присутствие правильных API не подтверждает их исполнение в целевой версии Unity/Mono.
NUnit использует тестовые endpoints и динамический реестр метаданных, а не настоящую
цепочку BepInEx 68 модов. Полноценные boot/game/coexistence/UI-тесты остаются обязательной
границей. Сравнение с XUnity: REUSE-DECISIONS.md.
